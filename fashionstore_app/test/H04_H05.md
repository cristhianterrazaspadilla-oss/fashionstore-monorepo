# H04 / H05 movil: implementado, pendiente de ejecucion

No se encontro Flutter/Dart disponible en el entorno de esta entrega. No se ejecuto
analyzer, compilacion, pruebas sqflite FFI, widgets ni una app movil. La lectura del
codigo no acredita funcionamiento SQLite. No se instalaron SDK desde la red.

## Cambios y conservacion

- LocalDatabaseService version 2 agrega origen verificado, referencias temporales,
  merma, cuerpo inmutable, huella y diagnostico. La migracion usa ALTER aditivo y
  conserva filas y la cola anterior; no borra turnos/cupos al cambiar sesion.
- Las consultas de caja requieren empresa, usuario y dispositivo. Sin contexto no
  existe fallback general. La sincronizacion recorre todos los turnos propios y
  envia cada cuerpo por su turno original. Los resultados completos quedan en SQLite.
- Una transaccion SQLite valida autorizacion/saldo, asigna secuencia y fecha con ancla
  central, consume cupo y agrega venta/comprobante. UUID repetido no vuelve a consumir;
  un cuerpo distinto es conflicto. El fallo intermedio revierte todo.
- Nuevas ventas exigen titular/dispositivo/habilitacion/rol/estado y ocho horas desde
  el inicio autorizado, ademas de una sesion valida segun SessionManager existente.
  Se detectan retrocesos de reloj observados; no es una garantia contra manipulacion
  del dispositivo. Vencimiento no libera cupos. Un cierre con pendientes se bloquea.
- El refresco conserva limites de consumo/mermas/liberaciones. Si falta el saldo,
  las ventas durables constituyen un limite inferior del consumo. Legado no verificable
  del turno mantiene conciliacion. Las ventas sin origen no se asignan al usuario nuevo.
- Legado con empresa/usuario/dispositivo/turno persistidos completos solo se revalida
  tras GET autorizado fresco y comprobacion de fechas/version. El legado ambiguo se
  conserva para revisar evidencia; la recuperacion supervisada no inventa su origen.
- Cierre/desactivacion no borran historial. Restaurar SQLite no resucita un turno
  invalidado explicitamente por central. La UI permite sincronizar sin turno actual
  y ejecutar recuperacion supervisada online sin reasignar ventas al supervisor.

## Pruebas preparadas

`unit/caja_h04_h05_sqlite_test.dart` usa SQLite FFI real, en memoria y en un archivo
temporal v1 que se cierra/migra/reabre; HTTP siempre MockClient. Cubre aislamiento,
varios turnos, reinicio, duplicados/conflicto, concurrencia por ultima unidad, rollback,
insuficiencia, vigencia/conciliacion, reloj/rol/dispositivo, saldo perdido,
conservacion, legado y respuesta perdida/reintento exacto con cambio de identidad.

Se adaptaron cinco suites heredadas de caja. `caja_fixture_aislada.dart` suministra
HTTP sintetico, metadatos de turno y dispositivo estable. Conserva los servicios y
persistencia reales; no constituye una prueba del backend ni de autorizacion JWT.
Las operaciones antiguas en memoria se sustituyeron por llamadas transaccionales
esperadas con await. Todas estas adaptaciones requieren ejecucion con el SDK.

```powershell
# Desde fashionstore_app, con Flutter y dependencias ya disponibles localmente.
flutter test --no-pub test/unit/caja_h04_h05_sqlite_test.dart
flutter test --no-pub test/unit/caja_offline_movil_test.dart test/unit/caja_sqlite_persistencia_durable_test.dart
flutter test --no-pub test/widget/caja_offline_screen_test.dart test/widget/caja_conciliacion_supervisada_test.dart test/widget/caja_flujo_productivo_completo_test.dart
```

No usar un backend real como respaldo si falta un mock o una dependencia. El primer
comando no necesita API, PostgreSQL ni proveedores. Revisar tambien el resultado de
analyzer/build con el SDK; ninguna de estas verificaciones se da por realizada aqui.

## Manual posterior en dispositivo de pruebas

1. Iniciar cajero A con red y habilitar un turno de una unidad. Consultar GET fresco.
2. Quitar red y cobrar efectivo. Reiniciar la app: recuperar pendiente y comprobante,
   mantener consumo. Rechazar segunda venta sin cupo y no permitir cierre.
3. Cambiar a empresa/usuario B: no ver ni enviar la operacion A. Volver a A y recuperarla.
4. Con fixtures de dos turnos, comprobar que la sincronizacion global usa T1 para una
   venta T1 aunque el actual sea T2. Mantener UUID/cuerpo ante perdida de respuesta.
5. Probar vencimiento y conciliacion: no cobrar ni devolver cupos; si el reloj
   retrocede respecto del ultimo observado, requerir verificacion online.
6. Supervisor de A: indicar turno original y recuperar con autorizacion central.
   Supervisor de B: rechazo. El titular original no se reemplaza por el supervisor.
7. Actualizar una copia de datos v1: no borrar ventas ni atribuir registros ambiguos.
   Revisar el contador/diagnostico de recuperacion. No usar limpiarTodo para migrar.

Contratos: mismas rutas y cuerpos de venta. Backend debe aportar empresa_id y
hora_central_en en la habilitacion/consulta. No se instalo SQL ni se accedio a la
base compartida. Concurrencia PostgreSQL y los constraints reales quedan pendientes
de pruebas aisladas. PWA corresponde a web y sigue fuera de este bloque; checkout,
pagos electronicos y CU27 tampoco se modificaron.
